# Recognition: the spec against the repository, and a build plan

**Status:** reconciliation for Kameel's review and for Fable's design pass. Written 2026-10-07 (Opus). No code, SQL or screen changed.
**Reads:** `docs/design/RECOGNITION_spec_v0.2.md` v0.2.3 (on `origin/claude/scrbrd-os-03vb2m`; not on `main`), measured against `origin/main` at `8ddc421` (db/86 the latest shipped file), the in-flight `origin/claude/wip-wicket-on-extra` (db/87) and the approved-for-after-the-pilot `GA-I36_corrections_everywhere.md` (on `origin/claude/wip-ga-corrections-design`).
**Reader:** Kameel first (§4's numbered questions), then the Fable agent who designs the four hard parts (§4.2), then Opus and Sonnet, who build §5 slice by slice.

The spec was written against the single-file prototype `scrbrd_os.jsx` and cites it by line. That file is not this repository. Every `L…` reference in the spec points at the prototype; every reference below points at this repository. Names in examples are positions ("the batter", "the captain"), never a child.

## 0 · In one page

**Most of Phase 0 is already met, some of it differently from how the spec imagines.** The repository is event-sourced: the ball log is the only truth (`docs/ARCHITECTURE.md` §2), every figure is a fold or a SQL view that the parity suite holds to the fold, and corrections are `void` events. So P1 (bowler credit), P3 (ball identity and an event log) and most of P4 (competition, result, playing conditions) are met. P2 is half met: the dismissed batter and the run-out end are structured, the fielder is not. P5 (a match captain) is deliberately not built: the captain is a season honour (ADR 0003, SCRBRD-138 D3). P6 is met on the server and not on the scorer's pad, whose live overlay is still its own counter with a hat-trick bug. P8 (a boundary flag) is not met.

**A recognition module already exists.** `honour` (awarded, never edited, withdrawn with a reason), `team_cap` (derived caps), `player_milestone` (derived fifty, hundred, five-for, hat-trick, career runs and wickets, caps), `milestone_notice` (the "once" for a live notice), `recognition()` (one read), `POST /api/honours` and the pupil's Honours tab. The spec's Colours are the existing `colours` and `half_colours` kinds. Player of the Match, nominations, personal bests, records boards, a fixture class, and staff recognition do not exist.

**The spec's role table (§11.2) does not match the repository's roles**, and several rows conflict with decided rules: the office awards honours today and the spec says it may not; the owner's key holds every school capability and the spec says a platform role decides nothing at a school; the spec lets a scorer nominate Player of the Match, which its own §9.1 does not; public record boards and a "public photo" consent are ruled out by `PUBLIC_DATA.md` (A3, A8).

**The recommended shape:** derive achievements, personal bests and records as views over the log (the `player_milestone` pattern), and store only what a person decides: awards, nominations, publication. `deriveFacts` (spec §8) becomes a pure module in `packages/scoring` that the pad, the commentary and the parity suite share, with SQL views as its mirror. Nothing new becomes a second place where a score is true.

**Build:** twelve slices (§5). Three can start right after the 15 October solo test without waiting for anyone: the pure facts module (R1), the pad overlay on it (R2), and the fixture class (R3, once Q1–Q3 are answered). Player of the Match waits on Fable's pass; record boards wait on R3 and R4; anything touching a correction waits on GA-I36's A2.

### 1.3 Other spec claims checked

- **Unlinked players hold nothing.** Met. A typed name has no `player` row; `striker_id` is NULL for it (`events.mjs` 1453, "see asPlayerId"), so `milestone_watch()` and `player_milestone` never see it, and the public page never names it (`PUBLIC_DATA.md` L6).
- **Super over never a milestone.** Met (`db/71` §5, `milestone_watch()` returns first; `ball_event_career`). The spec's §5.4 "super over: no board, no achievement" is already the repository's rule.
- **Backdated import ordered by performance date.** Met for derived milestones: career thresholds order by `starts_at` (`player_milestone`, `db/08` 5631–5655). A scorebook summary never fires a live notice (`milestone_watch()` reads `kind = 'ball'` only; `SCRBRD-120` §2.7 line 142), so "a past milestone is never shown as new today" holds.
- **Scorebook history is evidence, not deliveries.** A book's 104 is a `hundred` in `player_milestone` (it reads `player_innings`, which includes summaries since `db/64`), with no balls to 100. That matches spec §6 ("a final score of 104 can support a verified century; it cannot establish balls to reach 100"), but no read says which source a milestone came from (R4).
- **A correction takes a derived milestone with it.** Met for the views (`player_milestone` folds `ball_event_live`, which skips voids). **Not met for notices:** a fifty noticed on a ball later voided stands, and so does its notification (GA-I36 §0 item 1, D4; fixed by GA-I36 A2).

### 2.3 Where §11.2 conflicts with the repository's rules

1. **Platform roles hold no school.** `db/86` makes a school-scoped platform appointment impossible, but the owner's key is still platform-wide with every school capability. The spec wants "no school authority from platform role". The precedent for a carve-out is `safeguarding.*` (`roles.mjs` 101 and the RESTRICTIVE cut in `db/57`). Q6.
2. **`PUBLIC_DATA.md`.** A3: leaderboards across a competition are not public; SCRBRD-083 §5 (line 522): "Leaderboards (season, school records): **Never** … Signed-in only." A4: no public page per player. A5: the honours board shows only `honour.is_public` honours, names by L2 (initial and surname, with consent). A6: milestones appear on the live page under L2. A8: **no photograph of a pupil on a public page**. So the spec's `public` publication scope for records, its "public_photo" consent, and "public cross-school items" beyond A5/A6 conflict (Q11, Q12). Its anonymised label ("Hilton U15A player") is close to L2's position label ("Batter", "Player") and should be exactly that.
3. **A pupil's own view.** STEP4 §0 and line 585: the pupil's app is his passport; "no leaderboard of the team's parents' children on a family screen". The spec puts school record boards and personal bests on Profiles and Dashboard for players and parents. Fable F1, F5.
4. **The captain's view.** SCRBRD-138: the captain is the season honour (D2, D3); he writes nothing back in phases A and B, and a note to the side "needs an honour-gated publish" (D6); a coach sends nothing to him alone (D5, SG-9, `db/57` `recipient_is_pupil`). The spec gives him a time-limited `recognition_nominate` grant. A grant is a role assignment, and ADR 0003 says a captain is not a role. Fable F3.
5. **Separation of duties.** The repository's pattern is two capabilities held by disjoint role sets plus a row check: `scoring.amend.request` / `.approve` (`capabilities.mjs` 152–162, `cannot_approve_your_own`), `scoring.import.write` / `.confirm` with `two_people` (SCRBRD-120 §4). The spec's "a nominee never decides; switching role does not remove the conflict" fits that pattern; the spec's single `recognition_decide` held by a role that also nominates (headcoach both nominates and decides player awards) does not. `packages/policy/test/separation.test.mjs` is where the boundary is asserted.
6. **Live notices.** Spec §11.4: parent alerts use confirmed achievements only; §8: a live cue is tentative and "not official". Here `milestone_notify()` posts "Fifty for <full name>" to the side the moment the ball is recorded (`db/08` 5699–5718; team scope, `news.read`), before any seal. Push payloads name nobody (`services/api/notify/push-api.mjs` 63, `buildPayload`). Q9 and Fable F1.
7. **Season labels.** The school season is a calendar year, labelled `2026` (`season.label`, `db/08` 5043; `season_named(…, 'school')`); `recognition-api.mjs` 58–61 refuses "2026/27" for a school honour. The spec's examples ("— 2026/27") are a club season (Q14).

### 3.1 Where `deriveFacts` sits

Spec §8 asks for one pure function, shared by the overlay and persistence, over canonical ball events. Here:

- **The fold already exists.** `deriveInnings()` / `deriveMatch()` and the step-wise `foldSteps()` (`replay.mjs` 1168, 1220, 1605) give the innings state after every event. The commentary already walks `prev → cur` snapshots to raise milestones (`commentary.mjs` 600–663). `deriveFacts` is a **reader of that fold**, not a second reducer: `packages/scoring/src/facts.mjs`, exported from `index.mjs`, taking `deriveMatch()`'s output (or `foldSteps()`) and the roster index, returning innings-grain facts with the ball (`over.ball`, `seq`) at which each threshold was crossed: fifty and hundred crossings, five-for, hat-trick under Q8's rule, best figures and highest score candidates, balls to 50/100 where the innings has deliveries and `null` where it is a summary.
- **Who reads it.** The pad's overlay (replacing `detectMilestone()`'s own counting, R2), the commentary's milestone lines (one source for both), Player of the Match suggestions (R6, with the stat snapshot the spec wants stored as `derived_from`), and the parity test.
- **The SQL side.** Postgres cannot import the module, so SQL keeps its views (`player_milestone`, `bowler_innings_figures`, `bowler_hat_trick`) as the server's mirror, and `tools/smoke-fold-figures.mjs` folds the same logs both ways and holds the facts equal, as it already does for figures and results. This is the repository's established answer to "one canonical reducer" (`SCORING_RULES.md` "SQL agrees with the fold").
- **What it never does.** It writes nothing, decides nothing (an award is a person's), and treats a typed player, a super-over innings and a summarised innings's missing balls as "not attributable", never zero.
